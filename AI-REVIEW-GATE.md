# Codex-Claude Review Gate

Этот файл является общей точкой передачи изменений между Codex и Claude Code для GCSC/SmartContractor.

## Обязательное правило

Ни один deploy, merge в `main`, production integration, live payment, live loan, escrow, XPR action или публичная публикация не выполняется, пока изменение не прошло перекрестную проверку.

1. Автор создаёт отдельную ветку и файл `ai-review/records/YYYY-MM-DD-short-name.md` из шаблона `ai-review/TEMPLATE.md`.
2. Автор заполняет scope, риск, изменённые файлы, проверки и известные ограничения.
3. Второй агент проверяет diff и запускает проверки самостоятельно.
4. Автор исправляет все P0/P1. Второй агент повторяет проверку.
5. Только второй агент может поставить `Reviewer decision: APPROVED`.
6. Для live-risk требуется отдельное решение founder с безопасной ссылкой на evidence, без секретов.
7. Перед merge/deploy запускается:

```powershell
powershell -ExecutionPolicy Bypass -File execution/ai-review-gate.ps1 -ReviewFile ai-review/records/YYYY-MM-DD-short-name.md
```

8. Deploy разрешён только при результате `AI_REVIEW_GATE=PASS`.

## Правило «зелёное перед передачей» (один круг ревью)

Цель: ревью проходит **за один проход** (`READY_FOR_REVIEW` → `APPROVED`), без повторных кругов из-за того, что можно было поймать самому.

Перед тем как поставить `READY_FOR_REVIEW`, автор ОБЯЗАН:

1. Прогнать **весь** набор обязательных проверок задачи сам (node --check, полные тест-сюиты, `tsc --noEmit`, все относящиеся валидаторы, pg-smoke и т.д.) точно теми командами, которыми их будет гонять reviewer — без временных CLI-обходов (напр. без `--testTimeout`, если правка должна работать и без него).
2. Тесты, склонные к «мигающим» сбоям (тайминги, генерация ключей, сеть, БД), прогнать **2–3 раза подряд** и убедиться, что стабильно зелёные. Медленный Windows-runner founder'а — целевая среда; ориентируйся на неё.
3. Исправить **все** найденные проблемы **одним заходом** (не «починил одно → нашёл второе → новый круг»). Пройтись по всему списку находок ревьюера сразу.
4. В review-запись вписать точные команды и их результат (PASS/xx-of-yy), чтобы reviewer воспроизвёл в один проход.

Reviewer, найдя проблему, которую автор обязан был поймать по этому правилу, помечает её как процессное нарушение в записи. Дважды подряд у одного автора — правило усиливается.

## Где работаем

- Локальная запись и доказательства: `ai-review/records/`.
- Облачная зона проверки: Draft Pull Request на GitHub.
- Прямые рабочие изменения в `main` запрещены.
- Один PR содержит одну законченную задачу и одну review-запись.
- Автор и reviewer должны быть разными: `CODEX` и `CLAUDE`.

## Статусы

- `READY_FOR_REVIEW`: автор закончил первый проход.
- `CHANGES_REQUESTED`: reviewer нашёл обязательные исправления.
- `APPROVED`: reviewer подтвердил diff и проверки.
- `BLOCKED`: merge/deploy запрещён.
- `READY`: локальный review gate пройден; это не отменяет founder approval для live-risk.

## Live-risk

Следующие действия всегда требуют founder: production deploy, публичная замена сайта, секреты и внешние аккаунты, live Supabase, реальные платежи/займы/escrow, stablecoin/token collateral, XPR/FIO подписи, legal/provider commitments, мобильная публикация и destructive actions.
