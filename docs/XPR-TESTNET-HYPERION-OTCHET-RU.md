# XPR Network Testnet — сбой инфраструктуры истории (Hyperion): полевой отчёт

**Дата:** 2026-07-11
**От кого:** команда GCSC / SmartContractor (разработка на XPR testnet)
**Важность:** высокая для сторонних разработчиков — молча ломает любой dApp, который проверяет транзакции через Hyperion.
**Сеть:** XPR (Proton) **testnet**, chain_id `71ee83bcf52142d61019d95f9cc5427ba6a0d7ff8accd9e2088ae2abeaf3d3dd`

> Это русская версия отчёта для внутреннего понимания. Английская версия (для команды XPR) — файл `XPR-TESTNET-HYPERION-OUTAGE-REPORT.md`.

---

## 1. Коротко о главном

Наш платёжный поток (мобильное приложение → кошелёк WebAuth → перевод `eosio.token::transfer` → смарт-контракт → проверка на backend) не работал на **последнем шаге проверки** около 5–7 дней. Мы перебрали и отсекли все слои. Настоящая причина оказалась **на стороне инфраструктуры testnet, а не в нашем коде**:

> **API истории Hyperion в XPR testnet фактически недоступен. Единственный публичный узел, который ещё отдаёт `/v2/history/*`, отстаёт больше чем на месяц; все остальные адреса либо вообще не имеют этого API (`404 Unknown Endpoint`), либо лежат (`502` / нет соединения).**

Перевод **успешно проходил на цепи**, но его нельзя было найти ни в одном индексе истории. Поэтому проверка на нашем сервере через `/v2/history/get_transaction` всегда возвращала «не найдено» → платёж отвергался с ошибкой HTTP 400, хотя деньги уже были переведены.

## 2. Что мы строили

- Мобильное приложение (React Native / Expo, `@proton/react-native-sdk`): подрядчик покупает «лид-токен» за **50.0000 XPR**.
- Оплата — обычный `eosio.token::transfer` с аккаунта WebAuth на наш контракт `gcsctoken111`.
- Backend затем **независимо проверяет** перевод на цепи через Hyperion `/v2/history/get_transaction?id=<txid>`, сверяя получателя / сумму / memo / отправителя.

Это очень частый паттерн: **клиент говорит «я оплатил, вот хэш», а сервер проверяет это по истории цепи.** Он полностью зависит от рабочего индекса истории.

## 3. Симптом

На телефоне оплата проходила этапы:
`Contact endpoint → Sign in WebAuth → Broadcast transfer → Verify on Hyperion → Confirmed`

…и всегда умирала на **«Verify on Hyperion»** с ошибкой **`Verification failed: 400`** — уже **после** того, как кошелёк подписал и отправил транзакцию. Балансы доказывали, что перевод реально прошёл (баланс отправителя падал на 50 XPR при каждой попытке), но проверка всё равно проваливалась.

## 4. Полный путь поиска поломки (каждый слой по порядку)

Честный полный список всего, что мы проверили, прежде чем нашли настоящую причину. Делимся, чтобы другие команды узнавали проблему быстрее.

1. **Приложение не доходит до backend (401 вместо 402).** Не отправлялся валидный JWT. → Починили сессии; отличили 401 от ожидаемого 402-запроса оплаты.
2. **Приложение падало при запуске в собранном виде** («Native module is null», чёрный экран). → Проблемы AsyncStorage / New Architecture, отсутствовал `babel.config.js` с плагином worklets, не хватало крипто-полифилов, неверные версии зависимостей (reanimated vs worklets). Собранное приложение вело себя иначе, чем Expo Go.
3. **Expo Router «Unmatched Route»** при возврате из кошелька по deeplink. → Добавили маршрут `app/webauth-callback.tsx`.
4. **WebAuth показывал «Unknown Requestor».** → Добавили метаданные ESR `req_account`, теперь отображается как наш dApp.
5. **`esr://` deeplink не обрабатывался** («No Activity found to handle Intent»). → XPR WebAuth регистрирует `proton-dev://` (testnet) / `proton://`, а не `esr://`. Поменяли схему.
6. **«Need zlib to compress»** при кодировании ESR в React Native. → Кодировали без сжатия.
7. **Кошелёк открывался, но подпись не возвращалась** (`WebAuth callback timeout`). Логи устройства (adb logcat) показали, что WebAuth возвращается по **пустому** `smartcontractor://webauth-callback` (без `?sa/?sp`). Вывод: **прямой ESR-deeplink НЕ способен получить результат подписи от XPR WebAuth — результат отдаётся по каналу Proton Link, а не через deeplink.** Поэтому сделали **`@proton/react-native-sdk` (Proton Link) единственным путём** для подключения и перевода.
8. **`JSON Parse error: Unexpected character: <` при подключении/переводе через Proton Link.** SDK стучался на «chain API» адрес, который отдавал **HTML-страницу ошибки** вместо JSON. → Адрес, что у нас был (`https://testnet.xprnetwork.org`), — это **сайт-обозреватель, а не API-узел** (`/v1/chain/get_info` → `404` HTML). Переключились на настоящие chain API узлы.
9. **Вход работал, а перевод всё равно `JSON Parse <`.** Потому что вход не делает запросов к цепи, а перевод требует `get_abi` + `push_transaction`. Узел, что мы выбрали (`tn1.protonnz.com`), отдавал `get_info` нормально, но **`502` на `get_abi`**. → Перешли на более здоровые узлы с failover.
10. **Приложение зацикливалось на «Connect wallet» вместо оплаты.** Backend хранит кошелёк как `wallet.accountName`, а приложение читало `wallet.account`. Несовпадение имени поля. → Нормализовали.
11. **«No saved Proton Link session» на переводе.** Сессии входа SDK живут в памяти и теряются между запусками; восстановление не удавалось. → Делаем повторный вход перед подписью.
12. **«Пинг-понг» WebAuth** — кошелёк мелькал (открывался/закрывался) при переводе. Наш маршрут `webauth-callback` уводил приложение с экрана оплаты при каждом возврате фокуса, снося транзакцию. → Возвращаемся на предыдущий экран, а не уходим.
13. **`assertion failure: token does not exist`** — перевод дошёл до цепи и **наш собственный контракт его откатил.** Действие `transfer` контракта `gcsctoken111` запускалось на **входящих** уведомлениях `eosio.token` и искало `XPR` в своей таблице токенов (где только наш токен), с ассертом «token does not exist». → Добавили `if (this.receiver != this.firstReceiver) return;`, передеплоили.
14. **`Verification failed: 400`** на финальной проверке backend — **настоящая последняя причина (раздел 5).**

Слои 1–13 были действительно нашими багами и исправлены. Слой 14 — не наш баг.

## 5. Корневая причина (это уже сторона testnet)

Наш backend проверяет через `GET {узел}/v2/history/get_transaction?id=<txid>`. У него есть список узлов с failover. Мы проверили все адреса XPR testnet, что смогли найти, 2026-07-11:

| Адрес | `/v1/chain/*` (chain API) | `/v2/history/*` (Hyperion) | Заметки |
|---|---|---|---|
| `api-xprnetwork-test.saltant.io` | ✅ 200 JSON | ⚠️ 200 JSON, но **ОТСТАЁТ** | `last_indexed_block_time: 2026-06-04` — **>1 месяца назад**; `get_actions` активных аккаунтов возвращает `total: 0` |
| `testnet-api.alvosec.com` | ✅ 200 JSON | ❌ `404 Unknown Endpoint` | только chain, без Hyperion |
| `tn1.protonnz.com` | ⚠️ `get_info` OK, `get_abi` **502 HTML** | ❌ | наполовину сломанный узел |
| `testnet.xprnetwork.org` | ❌ `404` HTML (сайт) | ❌ | вообще не API-узел |
| `testnet.rockerone.io` | — | ❌ `502` | лежит |
| прочие (protonchain, eosusa, protonkiwi, protonnz, eosiomadrid, alcor, brotonbp, cryptolions, greymass, blokcrafters…) | — | ❌ лежат / без Hyperion | ни один не годен |

### Честный ответ на вопрос «узел один или есть другие, на которые можно переключиться?»

**Фактически рабочий узел с API истории Hyperion — только один, `api-xprnetwork-test.saltant.io`, и он застрял на месяц в прошлом.** Все остальные адреса либо не имеют Hyperion (`/v2/history` → `404 Unknown Endpoint`), либо офлайн. **Здоровой альтернативы для автопереключения нет.** Автоматический failover по нескольким узлам (мы его сделали) не помогает, когда актуального индекса нет **ни у кого**.

Поэтому перевод, прошедший на цепи, **не виден** для `get_transaction`, и любой сервер, проверяющий через Hyperion, его (обоснованно, со своей точки зрения) отвергает.

### Наш обходной путь

Так как перевод доказуемо на цепи (балансы меняются), но не индексируется, наш backend теперь:
- Пробует Hyperion с коротким повтором.
- Если **ни один узел не находит транзакцию** (недоступен/отстал, а не явное несовпадение) — **принимает платёж как `pending`** (HTTP 200) и оставляет фоновому верификатору сверить позже, вместо жёсткого 400.
- **Явные несовпадения** (транзакция найдена, но не тот получатель/сумма/отправитель) по-прежнему возвращают 400.

Это разблокировало нас, но это **вынужденное послабление из-за сломанной инфраструктуры testnet**, а не то, что мы бы выбрали. На mainnet или на здоровом testnet мы бы оставили строгую синхронную проверку.

## 6. Влияние на сторонних разработчиков

Любая команда на XPR testnet, использующая стандартный паттерн «проверять перевод на сервере через Hyperion» — платежи, faucet-ы, on-chain доказательства, индексаторы, аналитика, проверки «произошло ли действие?» — столкнётся с этим. Сбой **тихий и обманчивый**: транзакция проходит, кошелёк подписывает, деньги двигаются, и падает только *проверка* — поэтому разработчик естественно винит свой код подписи/кодирования/эндпоинтов (как мы несколько дней), а не индекс истории.

## 7. Просьбы к команде XPR Network

1. **Поднять хотя бы один надёжный, актуальный публичный Hyperion-узел testnet** и держать его под мониторингом. Лучше 2–3 для резерва.
2. **Опубликовать проверяемый (health-checked) список эндпоинтов** testnet, чётко разделяя:
   - **Chain API** узлы (`/v1/chain/*`), и
   - **Hyperion history API** узлы (`/v2/history/*`),
   с живым индикатором «время последнего индексированного блока» / отставания, чтобы разработчики сразу видели устаревание.
3. **Добавить баннер «известная проблема»** в документацию и в каналы для разработчиков, когда индексация testnet деградирует, чтобы люди не теряли дни на несуществующий баг в своём коде.
4. **Гайд для авторов dApp:** документировать, что история testnet может отставать, и рекомендовать паттерн graceful-degradation / асинхронной сверки (как `pending` выше), чтобы отставший индекс не ломал пользовательские сценарии.
5. Рассмотреть лёгкий, независимый от индекса способ проверки (например, надёжный `get_transaction` по id прямо с trace API полного узла), чтобы проверка не зависела только от доступности Hyperion.
