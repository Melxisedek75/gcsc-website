## Priority Order

### P0: Lock The Public Promise

Public headline standard:

> Construction trust infrastructure for verified project records, milestone evidence, contractor reputation, and provider-ready working-capital review.

Do not lead with blockchain, token, DeFi, DAO, smart-contract escrow, stablecoin, or collateral language.

Required public boundaries:

- GCSC does not originate loans today.
- GCSC does not hold escrow today.
- GCSC does not move customer money today.
- GCSC does not approve credit today.
- GCSC does not settle stablecoins today.
- GCSC does not custody tokens today.
- GCSC does not provide legal/provider decisions today.
- Future regulated integrations require founder, legal, provider, licensing, security, and technical approval.

### P1: Rebuild The First Viewport

First viewport should show:

- product name: SmartContractor by GCSC;
- role: construction trust infrastructure;
- audience: homeowners, contractors, and future providers;
- immediate value: organize bids, contracts, milestone evidence, disputes, reputation, and readiness packets;
- status: demo/beta preparation, not live finance.

First viewport should not show:

- token economics;
- investment upside;
- "decentralized escrow";
- "instant loans";
- "payments released on blockchain";
- "reputation as collateral";
- partnership-sounding Metallicus/XPR/FIO language.

### P2: Reframe Product Sections

Suggested section order:

1. Homeowner project request and contractor comparison.
2. Contractor profile and verification readiness.
3. Bid records and project contract records.
4. Milestone evidence and approval readiness.
5. Dispute evidence and peer review.
6. Contractor reputation and completion history.
7. Working-capital readiness packet for future provider review.
8. Admin audit trail and request IDs.
9. Future regulated provider/Web3 layer.

This order keeps the public story understandable without requiring blockchain context.

### P3: Keep Future Web3 As A Lower Architecture Layer

Use this framing:

> GCSC is designed so verified construction workflow records can later connect to approved provider infrastructure and, where legally cleared, future Web3 audit or settlement rails.

Do not use this framing:

> GCSC already connects contractors to blockchain loans, token collateral, stablecoin settlement, or Metallicus/LOAN services.

Future Web3 should appear only after the traditional product is clear, and only as:

- optional;
- staged;
- provider-reviewed;
- legal-review-required;
- not live;
- not a partnership claim.

### P4: Preserve Plug-In Ports

The product should keep these integration ports ready while operating as traditional-only:

| Port | Near-Term Function | Future Optional Function |
|---|---|---|
| Contractor profile port | business profile, license, insurance, reputation metadata | KYB/KYC packet, optional wallet mapping after approval |
| Project contract port | parties, scope, amount, terms, milestones | provider-reviewed contract record, optional audit hash |
| Milestone evidence port | photos, notes, status, readiness | escrow review packet, optional immutable evidence reference |
| Working capital port | readiness score, project context, repayment waterfall draft | licensed provider/lender review packet |
| Repayment context port | expected allocation and payment status | provider-managed repayment routing after approval |
| Dispute evidence port | evidence packet, peer review, admin notes | legal/provider packet, optional audit hash |
| Request-id/audit port | local request IDs and event logs | optional provider event reference or chain hash |
| Public wording port | traditional construction workflow language | reviewed Web3 language only after approval |

Each port should support these states:

- `traditional_only`
- `provider_ready`
- `future_web3_review_required`
- `live_approved` only after explicit founder/legal/provider/security/technical approval
